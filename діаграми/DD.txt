Опис структури (ERD - Сутності бази даних)
Замість старих таблиць тепер використовується оптимізована реляційна модель для підтримки кількох ігор на одного користувача:

Таблиця APP_USERS: Глобальний обліковий запис користувача у вебдодатку. Зберігає email, захешований пароль (для JWT-авторизації) та globalRating (середній показник імпакту по всім прив'язаним іграм).

Таблиця PLAYERS: Ігровий профіль (смурф, мейн). Зберігає специфічні ідентифікатори (riotId, steamId), тип гри (gameType — VALORANT, CS2, DOTA2), поточний ранг та агреговану статистику (середній K/D, HS%, GPM/XPM). Зв'язана з APP_USERS відношенням Many-to-One.

Таблиця MATCHES: Універсальна таблиця для зберігання історії матчів. Фіксує результати конкретної гри (кілли, смерті, асисти, мапу/агента/героя) та кастомний обчислений rating21. Зв'язана з PLAYERS.

Опис діаграми класів (Бізнес-логіка)
Структура стала модульною. Тепер замість одного PlayerService система використовує спеціалізовані компоненти:

PlayerController та AuthController: "Вхідні точки" (Endpoints) у систему. Приймають HTTP-запити від клієнта. AuthController видає JWT-токени, а PlayerController оркеструє запити на синхронізацію профілів і матчів.

API Services (ExternalApiService, FaceitApiService, DotaApiService): Технічні адаптери. Відповідають виключно за мережеві HTTP-запити до сторонніх сервісів (HenrikDev, Faceit API, OpenDota API) та парсинг їхніх JSON-відповідей.

BackgroundSyncService: Фоновий планувальник (Scheduler). Автоматично запускається кожні 2 години, опитує зовнішні API та оновлює актуальні ранги (currentRank) для всіх прив'язаних акаунтів, а також перераховує глобальний рейтинг.

AuthService та JwtService: Ядро безпеки. Відповідають за перевірку паролів (Bcrypt) та генерацію/валідацію безстанних токенів авторизації.

RatingService: Інкапсулює математичні формули. Вираховує "Rating 2.1" на основі K/D/A, ADR (для шутерів) та імпакту (для MOBA).

Repositories (AppUserRepository, PlayerRepository, MatchRepository): Інтерфейси Spring Data JPA для виконання CRUD-операцій у PostgreSQL без написання сирих SQL-запитів.

Тестові сценарії (Test Cases)
1. Розрахунок рейтингу (Unit Testing)

TC-01: Коректний розрахунок (Шутери). Вхід: 20 kills, 10 deaths, 150 ADR. Очікуваний результат: рейтинг > 1.0.

TC-02: Захист від ділення на нуль. Вхід: 15 kills, 0 deaths. Очікуваний результат: система не падає з ArithmeticException, застосовується fallback-коефіцієнт, рейтинг розраховується коректно.

TC-03: Розрахунок MOBA-імпакту (Dota 2). Вхід: 600 GPM, 650 XPM, KDA 5/2/15. Очікуваний результат: Rating 2.1 коректно зважує економічний імпакт та участь у вбивствах.

2. Інтеграція з зовнішнім API (Integration Testing)

TC-04: Успішна мультиігрова синхронізація. Запит на /sync/cs2/{nickname} та /sync/dota2/{id}. Очікуваний результат: статус 200 OK, дані обох ігор успішно розпарсено через відповідні сервіси.

TC-05: Обробка невалідних ідентифікаторів. Вхід: 64-бітний SteamID для Dota 2 замість 32-бітного. Очікуваний результат: метод convertToSteamId32 коректно нормалізує ID перед відправкою до OpenDota.

TC-06: Відмовостійкість стороннього сервісу. Вхід: Faceit API лежить. Очікуваний результат: система логує помилку, не "падає" з NullPointerException і повертає клієнту адекватний статус.

3. База даних та Безпека (Persistence & Security)

TC-07: Унікальність ігрових профілів. Спроба зберегти гравця, який вже є в базі для даної гри. Очікуваний результат: завдяки UniqueConstraint(game_type, steam_id), дублікат не створюється, запис оновлюється.

TC-08: Захист маршрутів (JWT). Спроба викликати POST /link/dota2/{id} без заголовка Authorization. Очікуваний результат: 403 Forbidden / 401 Unauthorized.

TC-09: Перезапис історії матчів. Повторна синхронізація матчів для одного гравця. Очікуваний результат: спрацьовує deleteByPlayerId, старі матчі видаляються, записується свіжий пул (запобігання дублюванню матчів).
